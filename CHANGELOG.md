# Changelog

All notable changes to this repository will be documented in this file.

## Unreleased

- Skills and evals: match documented tool outputs to what the MCP server returns. `flag-release` reads `match-release-policies` through `winningPolicy` (`releaseMethod`, `guardedReleaseConfig.metricKeys`) and says a held environment is left out of the rollout config; approval-blocked writes have no `approvalUrl` (share the created request's `approvalRequest.url`); `get-flags` `state` is `live`, `deprecated`, or `archived`; `update-flag` uses `makeFlagTemporary` and `makeFlagPermanent`; experiment treatments use `id`. Eval mocks for `toggle-flag`, release policies, experiments, metrics, and `get-sdk-key` now use the server's response shapes.
- All skills: match examples and instructions to the live MCP tool schemas. Mutating examples pass the required `confirm: true` (flag targeting, `copy-flag-config`, guarded rollouts, experiment iterations, approvals, AgentControl Config variations and rollouts). `launchdarkly-guarded-rollout` caps stages at 50% and gives metrics as `key`, `isGroup`, and `autoRollback`. `flag-release` records an immediate release as `{ environmentKey }` alone and a policy release with `releaseType: "policy"`; there is no `simple`. Server-side SDK keys come from `get-sdk-key` in `launchdarkly-metric-create` and `agentcontrol/projects`. `configs-targeting` and `configs-create` read targeting with `get-agent-configs` (`section: "targeting"`) and write it with `update-agent-config-rollout`, `update-agent-config-targeting`, and `update-agent-config-targets` instead of REST. Also fixes `copy-flag-config` (`sourceEnv`, `targetEnv`), `get-keys` (lowercase `productType`), and `update-agent-config-variation` (top-level `tools`). Evals add definitions and mocks for `create-project`, `get-flag-health`, `get-flag-status-across-envs`, and `update-agent-config-rollout`, require `verdict` on `recommend-flag`, and drop leftover old tool names.
- All skills: switch to the stabilized LaunchDarkly MCP tool names. Each resource has one `get-<resources>` tool that lists, or gets one item when passed its key (`get-flags`, `get-metrics`, `get-experiments`, `get-projects`, `get-agent-configs`, ...); `query-*` observability tools are now `search-*` with camelCase parameters; `check-removal-readiness` is `get-removal-readiness`, `find-stale-flags` is `search-stale-flags`, and the AI Config tools are the `*-agent-config*` family (`get-agent-configs` takes `section: "health"` for health checks, `create-agent-config-variation` takes `sourceVariationKey` to clone). Release Autopilot settings use `get-release-autopilot` and `update-release-autopilot` (`accountWide`). SDK keys come from `get-sdk-key`, and client-side IDs and mobile keys from `get-environment`. Eval tool definitions are regenerated from the server's schemas. Requires a hosted MCP server that exposes the new tool names.
- `experiments/launchdarkly-experiment-setup`: require the flag and variations, hypothesis, and primary metric from the user before creating anything; if the named flag does not exist, offer three choices in one message: correct the key, listing similar flags; create it themselves and then continue; or have the agent create it. For the last, propose the key, name, type, and variations, say it will be created off, follow `launchdarkly-flag-create` when that skill is installed, and wait for an explicit yes before `create-flag`. Never create a flag unless they pick that option and approve the details; add flag variations only when the user explicitly asks, and otherwise say which variations exist and ask; suggest a control from what the flag serves today, or the off variation when it is off, and ask instead when the flag is brand new (created in this conversation, or status `new`: created fewer than seven days ago and never evaluated), the targeted rule is a percentage rollout, or the flag is off and that environment is `inactive` (no one is currently being served the off variation); suggest `user` as the randomization unit only when `search-contexts` confirms it is the only context kind in use, and otherwise ask; label every suggestion with a one-line reason and let the user change it before approval; before showing a design, gather every missing piece in one message, and skip that message when nothing is missing; include a new metric's kind, basis, and measure when the user's wording has not already made them clear; show the design only when nothing is blank, then stop until the user approves it; create the metric and experiment only after the user approves a complete design they have seen; if they change anything after seeing it, show the updated design and ask once more; call `get-metric-events` only after a missing primary metric is known to be a custom event and the user has named its event key; if that event is not reaching LaunchDarkly, warn in the design, list at most 10 arriving custom event keys (preferring ones similar to the key the user gave), and let the user correct the key or approve as is; create the metric and experiment on approval even if it has not arrived; right before starting, call `get-metric-events` again for a custom-event primary metric and, if it is still not arriving, ask whether to start anyway, in the same message as the flag-off question when both apply. A metric name alone is not that key. Do not skip the flow check or block creation before the event is identified; start an iteration only after the user says to start. Omit `methodology` unless the user chooses one; the design shows statistics as LaunchDarkly default (frequentist, sequential testing) unless they chose otherwise, and a Bayesian choice is sent as `methodology` `"bayesian"`. When stopping, report significance for a frequentist experiment and probability to beat baseline or probability to be best for a Bayesian one (0.3.0).
- `onboarding` 0.4.0: add `references/sdk/observability-plugin.md` and load it from the SDK install when the user asks for observability, session replay, error monitoring, logs, or tracing. Covers browser (React, JavaScript, Vue), Next.js, Node.js, React Native, Python, Ruby, Go, .NET, iOS, and Android. The plugin goes on the existing client's `plugins` option and reuses its key. `recipes.md` points to the new reference instead of its per-SDK one-liners. The request is honored at any point, including a follow-up after onboarding finished; session replay defaults to strict privacy; an SDK too old for `plugins` gets a question before any major upgrade. Adds three onboarding evals for these paths.
- Claude Code marketplace: add `version`, `author`, `homepage`, `repository`, `license`, `category`, and `keywords` to the `launchdarkly` entry in `.claude-plugin/marketplace.json` so directory listings get the same metadata as `.claude-plugin/plugin.json`. A test keeps the two in sync.

- Rename `factory/launchdarkly-factory-settings` to `release-autopilot/launchdarkly-release-autopilot-settings` and switch it to the `*-release-autopilot-*` MCP tools (Claude Code plugin 1.0.2, Cursor plugin 1.0.3). Requires a hosted MCP server that exposes the new tool names.

- `factory/launchdarkly-factory-settings`: when GitHub is not installed or this member has not authorized, hand the user `githubConnectUrl` (the integration drawer's install or authorize page) and retry after they finish.
- Claude Code plugin 1.0.1: resolve plugin directory scanner findings. Replace the flat `skills/` symlinks with an explicit `skills` list in `.claude-plugin/plugin.json`, add `icon` and `privacyPolicyUrl`, and stop skills from auto-detecting API tokens in environment variables or `~/.claude/config.json` (prefer the MCP server's OAuth; ask the user for a token when a REST call is unavoidable).
- `factory/launchdarkly-factory-settings`: confirm before account-wide writes, maps, repo overrides, and unmaps; add a read-only "why didn't my PR get classified?" path (account gate, mapping, repo override).
- Refine `experiments/launchdarkly-experiment-setup` skill to match the LaunchDarkly REST API tool shapes: nested `iteration` on create, `mutableFieldsByStatus`-aware `update-experiment`, and the new `save-and-start-experiment-iteration` + `stop-experiment-iteration` tools.
