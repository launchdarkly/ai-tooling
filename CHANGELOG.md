## Unreleased

- Add `agentcontrol/legacy-sdk-migrate` 0.1.0: migrate an app from the legacy AI SDKs (`launchdarkly-server-sdk-ai`, `@launchdarkly/server-sdk-ai`) to the current handler-based SDKs, following [Migrate from the legacy AI SDKs](https://launchdarkly.com/docs/sdk/ai/migration). Inventories legacy calls, maps each to a convenience function, `config().invoke()`, or `graph()`, moves tools into `tool_handlers` / `toolHandlers` or a `Registry`, replaces trackers with automatic metrics (and `track_feedback` with `result.track_data`), ports `enabled=False` fallbacks to error handling and `inspect_config()` / `inspectConfig()`, and covers streaming, history, async judges, and graphs. `references/api-mapping.md` has before/after code in Python and Node.js using the handler factory names the packages export.
- `feature-flags/flag-release` 0.2.0 and `feature-flags/flag-and-release-change` 0.2.0: release with environment release plans instead of release policies, which the plans replace at GA. Each environment's default release plan decides how a flag rolls out there, and a stated release intent (now, hold, `notBefore`, segment, prerequisite) still overrides it per environment. Precedence is intent, then an explicit override, then a flag release plan, then the environment's default release plan. The preview reads each environment's default plan with `get-environment-release-plans` (it does not depend on the flag, so the orchestrator's plan phase uses it before the flag exists), and reads a flag release plan through `launchdarkly-release-plans` where one applies. An environment with no default release plan is held, with a pointer to the onboarding skill or the environment's release plan settings, and there is no fallback. A flag release plan that names a plan other than the default is recorded through the REST API (`environmentReleasePlanKey`, `LD-API-Version: beta`): the skill shows the curl command, and the user runs it in their own terminal with their LaunchDarkly API access token. The agent never runs it or reads a token. The skills no longer call `match-release-policies` or `get-release-policies`. Evals: both suites put SKILL.md in the agent's instructions (`inline_skill`, since the skill text does not load with builtins off), get the release plan tool definition and a guarded default plan mock, hide the release policy tools, assert the plan read, and add "default plan exists" and "no default plan" cases. A `flag-release` case with built-in tools and a planted `.env` checks that, for a non-default plan, the agent shows the REST command and does not run curl or read a token.
- Add `release-autopilot/launchdarkly-release-plans` 1.0.0 (Claude Code plugin 1.0.8, Cursor plugin 1.0.9): one skill for both kinds of release plan. Environment release plans: read, choose (the environment's default first, other complete plans as alternatives), create from starter plans (Progressive, guarded with rollback metrics whose `analysisUnits` match the unit, at most 50% per step, or Custom) after checking the randomization unit with `search-contexts`, set the default, and edit through the MCP tools; delete, and clear the default, through the REST API. Flag release plans: list, get, create, update in place, make default, and delete, and start a flag's release from one, through the REST API (`/api/v2/projects/{projectKey}/flag-release-plans`, `/flag-release-plans/{planKey}`, `/flags/{flagKey}/flag-releases`). An environment with no complete release plan gets one first (or is left out when the user declines), and the skill never invents or points at an incomplete plan. A flag release plan stores each environment's release plan key, so a later change to that environment's default does not update it. For each REST operation the skill shows the exact curl command (with `LD-API-Version: beta`), the user runs it in their own terminal with their own API access token and pastes the output back, and the skill reads that output to continue; the agent never runs a REST command or uses a token, and never asks for a token in the chat. The commands use curl because the MCP server has no flag release plan tools and `ldcli` 3.16.0 has no command for these endpoints. Before any create, the skill checks for an existing default (environment or project), names it with a short summary, and asks whether to use it, replace it, or create another; it also names incomplete plans. Modes: Apply (confirm every write), Read-only, and Record only for skills that confirm and write later. Starter plan definitions and the custom plan questions move here from onboarding's `references/release-plans.md`.
- `release-autopilot/launchdarkly-release-autopilot-onboarding` 1.1.0: release setup follows `launchdarkly-release-plans` in Record only mode for environment release plans and the project's flag release plan; onboarding keeps the wizard steps, the confirmation, the write order, and verification, and its own `references/release-plans.md` is gone. Step 7 shows what an update changes and notes that the plan keeps its release plan keys when an environment's default changes later. If the user skips it or it fails, it is a follow-up, auto-releasing stays on as picked, and the summary says Release Autopilot proposes no release on pull requests until the plan exists. A starter offer can be declined ("Not now"). Evals: a scripted `{ command, text }` answer stands for output the user pastes after running a shown command, and the provider's `scrub_ld_credentials` option removes LaunchDarkly credentials from the agent's shell, so cases check that the agent shows each command with the beta header, never runs one or reads a token, and reads the pasted output; the starter, guarded, no-contexts, and custom plan cases move to the new skill's suite, and onboarding adds flag release plan cases (with a shell, skipped as a follow-up with auto-releasing on, Preview, and an in-place update).
